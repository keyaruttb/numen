## 审稿意见

### §6.8 神经元与突触

对照表的主要数字和限定基本准确，但有几处应收紧：

- **“赫布律”只能作为类比，不能写成实现了赫布学习。** `reinforce()` 只在同次召回出现的记忆对已存在的边上，将 `fire_count` 加 1，并更新时间戳；它不新建边，也不改变 `weight`（[synapse.py:662](D:/_projects/whale-card-oss/docs/论文-记忆稳态/bundle/synapse.py:662)）。表里的“只有计数增长，没有权重随计数连续变化的学习律”已经说明了限制。建议把行首改为“赫布式类比：共现边的使用计数增加”，避免读者误以为边权会因此增强。
- **`LAYER_DECAY` 的区分成立。** `spread()` 每跳把电势乘以 `LAYER_DECAY * weight`，最多三跳；代码没有按时间衰减突触边权。`weaken(factor=0.5)` 则是在反馈触发时，将关联边权乘以系数并把 `fire_count` 减 1（下限为 0），不是随时间发生的衰减（[synapse.py:584](D:/_projects/whale-card-oss/docs/论文-记忆稳态/bundle/synapse.py:584)、[synapse.py:614](D:/_projects/whale-card-oss/docs/论文-记忆稳态/bundle/synapse.py:614)）。
- **`MAX_EDGES_PER_NODE=24` 是邻接表上限，不宜当作数据库硬上限。** `_load_adj()` 和增量邻接更新会截断每节点邻接表；`rebuild()` 写库时的注释是“按 id 顺序截”，但实际写入这段没有按节点实施 24 条边的截断（[synapse.py:570](D:/_projects/whale-card-oss/docs/论文-记忆稳态/bundle/synapse.py:570)）。表格若写“每节点最多 24 条边”，容易被理解成持久化图也严格满足。建议改成“扩散邻接表每节点最多取 24 条边”，并核对重建路径是否本来就想实现同一限制。
- **语义边“每节点最多 3 条”是建边候选限制，不是最终图度数限制。** 每条记忆最多选 3 个语义近邻，但被其他节点选中也可能得到语义边；最终邻接表又可能截断。建议把表述改为“一条记忆主动选择至多 3 个语义近邻”。
- “弱化”也应写清它会同时减计数：目前表格说“按反馈下调”略含糊。实现将边权压到最低 0.1，并将 `fire_count` 减 1。

真卡统计数字**不能只凭代码断言**。`stats()` 的口径是：边数为 `synapse` 行数；`nodes` 是不同 `a_id` 数，不是所有端点节点数；覆盖率则统计 `a_id ∪ b_id` 中的不同节点数除以存活记忆数；平均度是 `2 * 边数 / nodes`，这里的分母同样是不同 `a_id` 数（[synapse.py:680](D:/_projects/whale-card-oss/docs/论文-记忆稳态/bundle/synapse.py:680)）。因此，若你报告的平均度 17.05 用的是 `2E / 全部端点节点数`，它与代码口径不一致；若它确实按 `2E / COUNT(DISTINCT a_id)` 算，则一致。`fire_count` 均值与最大值不在 `stats()` 返回值内，需注明来自数据库直接聚合。论文的边类型计数合计为 18,928；覆盖率 99.6% 与“覆盖节点数 / 存活记忆数”的口径相符，但应说明快照和分母。

### §6.5 / §6.6：评价、复盘、自我认识

这两节整体比实现更克制的地方值得保留，但有些词容易把数据流程写成认知能力：

- `learn_eval` 按反馈更新价值和 verdict，适合称为“规则化的学习条目评价”或“证据状态标记”；“它回答的是‘我学到的东西还成立吗’”拟人化过强。实现基于预设反馈类别与阈值，并不独立检验事实真伪。
- `review` 将反馈按主题归组、按强度阈值生成底稿，可称“规则驱动的反馈汇总/复盘记录”。它不等同于自主反思，也不证明产出的经验正确。可把“证据不足时不下结论”收窄为“低于预设门槛时标记为 watch，不晋升为经验条目”。
- §6.6 已明确说“没有自我模型”，这点准确。建议将“印象层里的自己”解释为以 `self` 为主体的记录与统计，不要让“它知道自己是什么吗”标题被理解为已有自我认识能力。

### §6.7：升级层级、回滚与纪律

L1/L2/L3 作为**分类框架**大致合理，但回滚表述有超出代码保证之处：

- L1 的热调范围不等同于所有参数都能通过 meta 热更新；表格列出的 `fb_*`、`hf_*`、`WHALE_*` 应限定为“受支持的运行时配置项”。改回原值也不一定恢复先前已发生的状态变化。
- L2 的 `speech_policy` 有逐条更新与 `speech_policy_log`，旧文本可作为人工恢复依据，但需避免暗示系统自动回滚策略更新。
- L3 的 git 回滚是仓库操作；`_schema_heal()` 是幂等补表/迁移机制，不等于回滚。把两者写在同一“可回滚方式”栏会混淆代码版本回退和数据库迁移。建议拆成“代码版本回退”和“数据迁移兼容/修复”，并明确迁移本身不保证可逆。
- 三条纪律目前主要是**方法规范，不是通用执行机制**。E1 预注册是实验设计；“改前留基线”“一次只改一处”并没有在这些实现文件中形成强制闸。回归闸目前仅接在梦境摘要压缩路径，论文 §3.8 已说明合并和侵蚀升级尚未接入。建议把“必须”改成“本文采用的实验纪律/建议流程”，或明确列出只在何种操作上由代码强制执行。

### E1b 的负结果措辞

“答得对但显示不出来是当前系统的主要损失形态”过强：实验是在 85 个有证据轮上，用当前一次召回结果外推权重，没有模拟未来检索、候选变化或重新排序；“答得对”也不是实验测量项。表中三臂的 R@K 不变，支持的是当前打分与外推权重无关；证据可见率下降，支持的是**按当前显示闸和这批命中证据外推时，可见性会快速下降**。

建议改为：

> 在这批冻结问题的一次召回结果上，按当前权重曲线外推时，三种衰减臂的候选排序未变；这是因为该检索打分中的权重系数为 0。与此同时，已命中证据中满足显示阈值的比例随外推时间下降。该结果表明，在当前实现与评测口径下，权重衰减影响证据显示，不影响候选排序；它不能据此说明系统未来回答正确率如何变化，也不能把未显示证据直接等同于“本可答对”。

另外，“所有时间点上一厘不动”可改为“在本次固定候选及分数计算中不变”；“主要损失形态”删去或限定为“本评测口径下观察到的损失形态”。

### 若只能再做一个实验

选择**阈值敏感性 + 完整 R@K/覆盖率曲线**。它能检验当前结论是否由单一显示阈值 `0.15` 或单一 `K=13` 口径驱动，也能把“显示、召回、覆盖”的权衡呈现出来。

设计上应预先固定冻结集、代码版本、权重外推规则和候选生成流程；在多个预先声明的显示阈值与 K 值上报告 R@1、R@3、R@K、证据显示率、覆盖率及置信区间。阈值和 K 的网格需在看结果前确定，完整报告所有组合，不挑最好看的区间；把当前系统参数标为基准点，另报告各设置相对基准的变化。结论只描述曲线上的权衡，不预设“降低阈值有益”或“权重应参与排序”。
