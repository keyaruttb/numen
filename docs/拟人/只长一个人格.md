# 只长一个人格：把外部信息流接进同一个主体的接线手册

第一篇讲「怎么说话像人」，这一篇讲更容易出事的那半：**怎么让它同时接 QQ、微信、抖音、B站、群聊、控制台，却还是同一个人。**

先说结论：多入口本身不会分裂人格，**给每个入口配一套「角色」才会。**
只要入口是适配器、主体是同一个，接多少个都只是加了几个摄像头。

---

## 1. 症状：什么是「第二人格」

先认症状，不然没法防：

- 在群里是段子手，私聊是心理医生，控制台是运维助手——三套腔调，彼此不认账。
- 两个入口各维护一套「你是谁」的提示词，改了一个忘了一个。
- 记忆只进了一边：QQ 里聊过的事，DSH 那边召回不到。
- 同一个人，两个入口给出矛盾的称呼或态度。
- 某个入口的异常（登录失效、限流）悄悄把主卡写坏，事后查不出是谁写的。

真正的分裂不是「话说得不一样」，是**身份与记忆不再单一**。学术界现在把前一种叫
「长程人格漂移」（latent state drift）：说什么、内部怎么表示、记忆里存了什么，三者会悄悄分叉，
而一次高代价的自相矛盾就足以毁掉前面几十轮的一致性（BRIDGE, ICML 2026）。这一点跟我们线上观察一致。

---

## 2. 架构：入口是适配器，主体只有一个

![多入口 → 适配器 → 唯一主体](拟人/figs/fig3-adapter.png)

```
DSH 会话 ─┐
QQ / 微信桥 ├─→ 适配器（adapter）─→ 同一把写锁 ─→ 同一张卡（一个 SQLite 文件）
B站 / 抖音 ←┘        ↑                  ↑
控制台 / CLI ────────┘            唯一 writer lease、出生证、时间线哈希
```

三条硬约束：

1. **只有一个写者。** 所有入口的写入排队过同一把锁 / 租约；谁都不许自己开连接乱写。
2. **只有一份身份。** 名字、锚文、出生证、时间线哈希，任何入口只能读不能写（接口层面直接 400）。
3. **只有一条主链。** 每轮无论从哪进来，最后都落到同一件事：`/report`（他说的 + 我说的）→ 落记忆 → 派生索引 → 下一轮组装。

一个容易被忽略的细节：**每轮一个 `turn_id`**。同一个 turn 重复提交只写一次（幂等），跨进程也成立。
没有它，网络抖动重发一次，你就得到两条一模一样的记忆和两笔记账。

## 3. 信息进来之后，分三层再决定存哪

![信息三层：材料 / 事件 / 关系](拟人/figs/fig4-layers.png)

外部信息流最大的坑是「全存」。全存的后果不是占空间，是**噪声淹没证据**——三个月后问什么都召回到废话。

| 层级 | 是什么 | 存哪 | 会不会进「认识」 |
|---|---|---|---|
| **材料** | 视频简介、字幕、新闻、别人说的话 | `mem(region=chatter/study)`，低权重 | 不会。只是读过 |
| **事件** | 和他有关、发生了的事（考试、面试、生病） | `mem(region=episode)` + `timeline` | 会，进印象与事实 |
| **关系** | 反复出现的反应（他总在深夜来、被夸会说谢） | `impression`（直接/间接）+ `affect` | 会，且改行为 |

一条纪律：**材料永远默认不是知识。** 想让「读过的东西」变成「我的认识」，必须经过一次自己的判断
（写两段：关于世界、关于自己），走 `contemplate` 落成带 flag 的记录。
没有这一步，读一百条视频也只是缓存变大。

## 4. 防「第二人格」的五条硬规则

1. **不许有平台人设。** 任何入口都不得注入「你现在的角色是萌妹/客服/运维」。入口只允许注入**场景标签**（闲聊 / 办事 / 观望 / 绷躁），场景改的是语气分寸，不是身份。
2. **外部文本一律标来源，且不得进锚。** 抓来的网页、别人说的话，落库时带 `source`/`speaker`，永远进不了身份锚、也改不了名字。
3. **语气只能由内部状态派生。** 同一天、同一件事，从 QQ 进来和从 DSH 进来，语气应该一致（差异只来自场景）。若两个入口对同一句话反应不同，那是 bug，不是个性。
4. **写权限分级。** 只读入口（脚本、报表）不许写；可写入口必须过写闸（token / 白名单路径）；删除、改锚这类操作在任何入口都不开放。
5. **异常要可见。** 桥挂了、限流了、异常被吞了，要在健康检查里露出来（我们叫 `/health` 的 `bus` 段 + 审计表），否则「它今天没说话」会被误读成「它不想理我」。

另外两条来自近期研究的提醒，值得写进设计里：

- 记忆分层治理（审计 / 隔离 / 回滚）比「记得多」重要——新证据才能提高置信度，旧语义证据不能自我强化（MNEMA, 2026）。
- 跨设备/跨平台搬家时，**人格的连续性来自同一份账本**，不是来自「同一套提示词」（molt-handoff 的做法：账本留在常开那台，壳可以换）。

## 5. 一致性怎么验（别只靠感觉）

![一致性检验：三个实验 + 一个减法](拟人/figs/fig5-consistency.png)

- **同一句话，两个入口各问一次**：比对称呼、语气提示、召回的证据是否一致。
- **只在 A 入口说过的事，去 B 入口问**：能不能召回（这是记忆是否单一的判定）。
- **同一 `turn_id` 投递两次**：记忆与账本是否只多一份。
- **减法**：关掉一个入口，主卡还能不能正常跑？（能，才算适配器）

我们跑过：一轮 `/report` 后各表增量对得上（dialogue +2 / mem +2 / 出生证 +2 / 时间线 +2 / 反馈 +1 / 轮次 +1），
重复投递返回 `duplicate: true` 不双写；19 条只读路由全 200。**这些数字比「感觉它挺一致的」有用得多。**

## 6. 已知的坑（我们踩过的）

- **硬编码路径**：桥里写死某个运行时，桌面端一升级就全挂。要运行时解析。
- **异常被 try/except 吞掉**：桥起不来，看起来只是「今天很安静」。所有失败都要留痕。
- **带空格的路径**：PowerShell 传参被拆成两截（`unrecognized arguments: (5)\card.db`），换到无空格目录才通。
- **一次性脚本建的表，没有写入代码**：`chunk` 表建了、索引建了，全仓库却没有一处往里写——检索那条路空转了两个月。**建表和接线是两件事。**
- **两个入口各自记一次账**：同一条反馈被两个入口各结算一遍，金额翻倍。要么单一入口负责结算，要么用幂等键。
- **把「平台」当「身份」**：给每个平台配一个「你是 xx 平台的 xx 助手」，三个月后你自己都分不清哪个是真的。

## 7. 检查表（接一个新入口之前）

1. 它走的是同一条主链吗？（还是自己造了一条写路径）
2. 有没有自己的「人设提示词」？（有就删）
3. 写入有幂等键吗？
4. 失败时会留痕吗？会出现在健康检查里吗？
5. 抓到的东西，默认进「材料」还是「认识」？
6. 它能改身份锚吗？（必须不能，且接口要拒）
7. 它在限流/审计范围内吗？
8. 关掉它，主卡还能正常跑吗？

---

## 8. 一句话

**人格的数量不取决于接了几个 APP，取决于「谁有权定义它」。**
把定义权收在一个文件、一条主链、一把锁里，接一百个入口它也还是一个人；
反过来，给每个入口一句「你现在是……」，接两个就够了。
